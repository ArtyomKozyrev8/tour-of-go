### 1. Защищайте каждую отправку и чтение через `select`
Каналы в Go блокируют поток намертво. Если вы отправляете или читаете данные без `select`, вы слепо верите, что на том конце кто-то вечно готов отвечать. Если читатель уйдет или случится таймаут, горутина превратится в «зомби» и навсегда утечет в память.

Всегда давайте рантайму альтернативный выход через `context`.

* **❌ Как НЕ надо:**
  ```go
  outChan <- result // Если получатель перестал читать (например, при Ctrl+C), тут будет вечный дедлок
  ```

* **✅ Как НАДО:**
  ```go
  select {
  case <-ctx.Done():
      return // Мгновенно выходим и не плодим утечки горутин
  case outChan <- result: // Пытаемся отправить, пока контекст жив
  }
  ```

### 2. В конкурентной среде `for + select` всегда надежнее, чем `for range`
Конструкция `for range` лаконична, но она абсолютно «слепа» к контекстам — она умеет реагировать только на закрытие самого канала (`close(ch)`). Если воркер застрял в ожидании данных из пустого, но еще не закрытого канала, он проигнорирует сигнал отмены приложения, и горутина зависнет.

Бесконечный цикл с явным `select` внутри дает полный контроль над ситуацией на каждой итерации.

* **❌ Как НЕ надо:**
  ```go
  for val := range inChan { // Если в канале пусто, заблокируется тут и проигнорирует отмену ctx
      // Обработка...
  }
  ```

* **✅ Как НАДО:**
  ```go
  for {
      select {
      case <-ctx.Done():
          return // Мгновенно реагируем на отмену, даже если в канале нет задач
      case val, ok := <-inChan:
          if !ok {
              return // Канал закрылся продюсером — планово завершаем работу
          }
          // Обработка val...
      }
  }
  ```
